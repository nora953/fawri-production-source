# FAWRI V1 — owner-approved full POS deferral, source cutoff implementation

**Owner decision:** 2026-11-11. Exclude the **entire Cashier/POS/offline subsystem** from the first commercially sold Fawri release, without deleting/rewriting existing financial or device data; exclude its subscription seats and new financial operations. **This is approval of product scope, not hosted deployment, source P0 gate closure or permission to dispose of historical receipts.**

**Source branch:** `fix/p0-provider-receipt-order-discovery-20261015`, Draft PR #550. Commercial release decision remains **NO-GO**.

## Implementation and proof boundaries

1. **Global server API cutoff**: `artifacts/api-server/src/middleware/firstCommercialPosCutover.ts` and `src/app.ts`. In `NODE_ENV=production`, independent of any toggled env flag, the first middleware rejects `/api/cashier/*` plus nested `/api/admin/merchants/:id/cashier/*` and `/api/auth/admin/merchants/:id/cashier/*` **before authenticators, staff, operator, sync, entitlement, any legacy route and storage response**. Verifies direct GET/POST and percent-encoded routes with no downstream invocation. Status `403 FAWRI_V1_POS_NOT_OFFERED`, no-store. It rejects direct `/cashier.html` and `/manifest.webmanifest` with **410**, also before serving static assets or SPA fallback. No SQL/IndexedDB delete occurs.
2. **SaaS billing remains independent**: `/api/billing/checkout`, `/api/reports/online` and merchant orders are not blocked. The SuperQi sandbox webhook is **shared** between SaaS and historical cashier invoices, so do NOT ban it. `superQiSandboxWebhook.ts` first persists verified payment evidence; if the verified order belongs to `cashier_subscription` under production V1, it fails **503 FAWRI_V1_POS_PAYMENT_HELD_FOR_RECONCILIATION** *before* cashier seat activation, allowing later provider retry/review **without losing the verified financial receipt**. SaaS subscriptions remain on their original branch. The isolated HTTP test checks ingress/mount order and source branch ordering; it is **not** an actual paid provider/hosted settlement proof.
3. **Frontend commercial cutoff:** `App.tsx` direct cashier management/report and combined report URLs render unavailable; `ReportsPage.tsx` shows online orders only; `SubscriptionPage.tsx` no longer renders POS upsell; `useMerchantFeatureEntitlements.ts` does not request/reveal cashier seats when compiled for commercial release. Sidebar/BottomNav already depend on these entitlements and therefore hide POS links. Original order/product/conversation/SaaS screens remain unchanged.
4. **Commercial bundle excludes independent POS:** `vite.config.ts` compiles `VITE_FAWRI_V1_POS_DISABLED='1'` for **every build** irrespective of external build `NODE_ENV`, omits the standalone `cashier.html` entry, and supplies a **retirement-only** `cashier-sw.js` and merchant-only manifest. `cashierMain.tsx` separately refuses operator-session recovery, automatic financial sync or offline SW registration if an accidentally served legacy entry is compiled under the disabled flag. The retirement worker does **not** delete CacheStorage, IndexedDB, outbox records or receipts; it unregisters its obsolete offline interception on the next online update.
5. **Keep historical safety tests:** development source remains testable for future recovery/archaeology, but production V1 cannot be re-enabled through `FAWRI_V1_POS_DISABLED=0`; moving POS into a future commercial version requires a separately reviewed source/profile/hosted safety release.
