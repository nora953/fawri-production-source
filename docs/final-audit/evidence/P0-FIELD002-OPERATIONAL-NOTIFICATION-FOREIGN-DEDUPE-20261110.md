# P0 FIELD002 — Reject phantom operational-notification dedupe across merchant/source

**Date:** 2026-11-10. **Parent P0 gate:** `P0-RESIDUAL-MERCHANT-PRIVACY-001/http` (**OPEN**). **Scope:** bounded source correctness for operational notification producer idempotence, notably financial payment-conflict notices. No actual hosted commercial gateway or payment accepted.

## Source defect

The operational producer in `artifacts/api-server/src/services/postgresOperationalNotificationAuthority.ts` already used atomic `INSERT ... ON CONFLICT (id) DO NOTHING RETURNING id`, eliminating the earlier two-winners race, but its **conflict case** unconditionally returned `deduplicated:true`. A notification ID that already existed for a **different tenant, unexpected type/source, or changed payment-event payload** was therefore falsely reported as an accepted duplicate. This could silently suppress a new `operational_payment_conflict` alert or misrepresent delivery evidence, despite PostgreSQL correctly preserving the unrelated stored row.

[Source fix `14c00696`](https://github.com/nora953/fawri-production-source/commit/14c0069648dc6079a4be1af3938062e71c89001e): retain the atomic insert. If `RETURNING id` is empty, check via the existing **merchant-scoped PostgreSQL transaction** that the durable row matches **exact ID, merchant audience, merchant ID, account ID, notification type, title/body template, source entity type+ID, and full immutable JSON payload**. Only then report a legitimate duplicate. Any foreign, absent, altered or maliciously reassigned ID fails closed with `OPERATIONAL_NOTIFICATION_SOURCE_CONFLICT`, without overwriting the stored notification. The `created_at` timestamp is intentionally not compared: a legitimate replay may supply a later timestamp but must leave the original timestamp untouched. No new notification type or source admission rule added.

## Limits / remaining gate

This proves fail-closed **integrity under conflict**, not that an external attacker can choose an ID. It does **not** prove signed hosted payment/provider data, actual deployed runtime/auth/operator identity and SQL+HTTP full-role parity, or historical notification producer retention. Previous accepted exact multi-tenant concurrent inserts remain in force; no claim of a newly closed top-level P0 gate.
