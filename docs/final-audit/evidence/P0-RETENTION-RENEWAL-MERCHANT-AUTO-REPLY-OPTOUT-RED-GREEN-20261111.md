# P0 retention — merchant auto-reply opt-out survives account renewal (actual RED → GREEN)

**Checkpoint (Baghdad local):** 2026-11-11. **Scope:** one source defect fixed on Draft PR #550 and proven in disposable real PostgreSQL with independently authenticated restricted merchant issuer. **Not hosted acceptance, signed-provider payment activation, data-deletion retention policy approval, or launch authorization.**

## Reproduced unauthorized preference reversal

`refreshMerchantRetentionPostgres` reinstated an otherwise legitimately activated/unexpired subscription after retention suspension by writing `subscriptions.auto_reply_enabled = ($2::subscription_status = 'active')`. This treats **subscription state** as merchant consent, overriding a durable `merchant_settings.auto_reply_enabled = FALSE` preference and activating replies after account renewal. The subscription had been automatically suspended with `auto_reply_enabled = FALSE`; that field cannot reconstruct the user's prior setting, which remains in merchant settings.

- **RED:** [test-only SHA `d72f8cd6`](https://github.com/nora953/fawri-production-source/commit/d72f8cd6ef3516deac62a7c5aa385bb6123a3074), [real restricted-login PostgreSQL and mounted HTTP workflow #42903449096](https://github.com/nora953/fawri-production-source/actions/runs/42903449096), **COMPLETED FAILURE on the newly added negative**: `AssertionError expected: false, actual: true`. Added distinct eligible active subscription rows for stored merchant opt-in, stored merchant **opt-out**, and **absent** settings; all merchant/settings/subscription rows synthetic in disposable Docker PG, cleanup registered. The old implementation reactivated automated replies for an explicitly opted-out merchant. Existing full-app HTTP tests before the new negative had no confirmed failure. This is a source defect demonstrated on synthetic merchant data, **not evidence of real commercial abuse**.

## Narrow source fix

- [Production source `f39ed261`](https://github.com/nora953/fawri-production-source/commit/f39ed261c7de7f1286b41b46c7b9d6edcde563ca): in the **same locked merchant authentication transaction and same subscription UPDATE**, set `auto_reply_enabled` only when `$2::subscription_status = 'active'` **and** `EXISTS(SELECT 1 FROM merchant_settings WHERE merchant_id = $1 AND auto_reply_enabled IS TRUE)`. If the settings row is absent (or invisible under a permitted RLS SELECT), the expression returns **false**, never inventing an opt-in. If the AUTH LOGIN lacks table SELECT privilege entirely, PostgreSQL instead rejects the transaction (fail-closed); **this is not evidence that hosted grants are sufficient**, and hosted role parity remains blocked. No new table/column, journal, migration, privilege or separate cross-tenant query; uses the existing merchant-scoped setting as authoritative preference. The account may resume after authenticated renewal while automatic replies remain off until a permitted merchant choice.
- [Source-derived assertion `ce0d8db9`](https://github.com/nora953/fawri-production-source/commit/ce0d8db91176ef1b58a80c409d4b1f2f4a82a42d) requires the merchant-settings `EXISTS` clause in the actual executed SQL rather than accepting the old unconditional boolean. The already accepted `pending_activation`, `suspended`, `expired`, `replies_exhausted` and stale-cookie denial contracts remain intact.
