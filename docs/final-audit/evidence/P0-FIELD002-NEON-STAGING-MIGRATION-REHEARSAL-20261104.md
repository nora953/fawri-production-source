## Confirmed PostgreSQL 18 owner-membership semantics (external reference) — 2026-11-04

The role bootstrap failure was cross-checked against official **PostgreSQL 18 Role Attributes** documentation ([Section 21.2](https://www.postgresql.org/docs/18/role-attributes.html)). PostgreSQL automatically grants a newly created role back to a **non-superuser CREATEROLE** creator with **ADMIN TRUE, SET FALSE, INHERIT FALSE**. The administrative grantee can later grant itself SET/INHERIT; the automatic grant is made by the bootstrap superuser and cannot be revoked/changed by the non-superuser creator. This exactly matches the observed `cloud_admin`-grantor / `neondb_owner` grantee in Neon and explains both the blocked `ALTER FUNCTION OWNER TO` and why the temporary SET grant+revoke did not achieve a zero-membership role.

**Safe closure options, none yet authorized/executed on the original branch:** a genuinely trusted superuser-equivalent provisioner must prepare a vetted NOLOGIN, NOBYPASSRLS, NOCREATEROLE, zero-member function-owner role and grant only the narrowly reviewed function-ownership handoff; or the project must explicitly approve a *different reviewed ownership security model* supported by Neon, with new negative tests. A plain `CREATEROLE` / Neon role API role is **not** a zero-member owner, and claiming it is would be wrong. Do not request or expose database passwords, grant elevated ADMIN/SET to the application login, or weaken the no-membership invariant without a separate decision.

The current migration's pre-existing-role `ELSIF` membership check does **not** re-check memberships after the new-role `CREATE ROLE` branch; this is source-level hardening work for a separate reviewed change, not proof that 0052 ever safely applied. No source migration file changed here.
