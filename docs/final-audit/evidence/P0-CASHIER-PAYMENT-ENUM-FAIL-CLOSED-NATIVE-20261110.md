## Reconciled finding, including corrected hypothesis

An initial review of repeated SKU lines suggested that each clone of a catalog entry might separately decrement the same stock item. **Actual CI demonstrated that this path is already rejected by `resolveCashierSalePricing` as `CASHIER_SALE_PRICING_CATALOG_AMBIGUOUS` before writes**, so an oversold completed sale from duplicate lines **was NOT proven**. An unneeded aggregate-stock modification (commit `6c487ac`) was **reverted** in [`a1ecc4ac`](https://github.com/nora953/fawri-production-source/commit/a1ecc4ac2cd507201fa4b4cf3297473f6c203a58), preserving the existing deliberate one-line-per-SKU business policy. The updated browser regression verifies this denial leaves ALL IndexedDB stores and sequence unchanged. Failed exploratory test runs are not accepted P0 evidence.

A **separate confirmed source gap** in `artifacts/fawri/src/lib/cashierIndexedDbAuthority.ts` was that `CashierCommitSaleInput.payment_method` and `payment_status` were only TypeScript union declarations; the runtime checked `payment_status='failed'` but did **not** reject unknown values such as `voucher`, `' cash '`, `cancelled` or an empty string. An untyped or restored caller could commit an invalid immutable sale/outbox envelope and consume a trusted device sequence, leaving an unreconcilable operation before server admission. The correction [commit `37bac34d`](https://github.com/nora953/fawri-production-source/commit/37bac34d0339aa376fa7566219b2129d89e69180) enforces exact known method values (`cash`, `card`, `electronic`, `other`) and known status values (`paid`, `pending`) **before opening any IndexedDB write transaction**. The pre-existing `failed` rejection retains its original distinct error code. It does **not** change payment processing rules, authorize unknown providers, or mark pending payments settled.
