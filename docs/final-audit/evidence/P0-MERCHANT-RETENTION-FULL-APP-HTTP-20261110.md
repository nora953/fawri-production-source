**Date:** 2026-11-10. **Status:** bounded source/actual disposable SQL and full-application HTTP **PASS**. Parent `P0-RETENTION-PRIVILEGED-DELETION-POLICY` remains **OPEN**; hosted release **NO-GO**.

## Closed evidence gap

The earlier [retention source fix](https://github.com/nora953/fawri-production-source/commit/5b199e72a04d9d1dfb0bad10c9aa46c57c8fc8c9) disallows reactivation of a retention-suspended account solely because a `pending_activation`, `suspended` or `expired` subscription has a future `expires_at`. Earlier [5/5 source tests](https://github.com/nora953/fawri-production-source/actions/runs/42750820065) and [actual isolated PostgreSQL issuer proof](https://github.com/nora953/fawri-production-source/actions/runs/42757846149) were accepted. They did **not** exercise stale merchant session cookies and actual application HTTP route writes.

The new [full-app authenticated HTTP integration](../../../artifacts/api-server/tests/merchant-retention-full-app-http-postgres.integration.test.mjs) imports the real `artifacts/api-server/src/app.ts` and makes actual `fetch` requests to `/api/auth/notifications/:id/read` and `/api/auth/notifications`, through `enforceMerchantRetentionAccess`, the production session/auth handler, merchant notification router and a real separate restricted authentication LOGIN. It runs **only** inside the existing network-isolated Docker disposable PostgreSQL **16** audit, not original Neon/Railway.

It seeds two independent synthetic merchants and real account/session cookies. The primary merchant initially has a genuine active future subscription and can PATCH its own notice. Then the disposable test fixture makes the subscription `pending_activation` and retention-suspends the account, keeping its **previously valid cookie** to test a stale request. Actual `refreshMerchantRetentionPostgres` refuses reactivation; subsequent HTTP PATCH is denied with 401/403 **without modifying either merchant notification**. The unrelated merchant still works and cannot PATCH the primary merchant's row (404). Only after an explicit **test-only administrative fixture update** to a genuine `active` future subscription and real `refreshMerchantRetentionPostgres` does a **fresh authenticated session cookie** successfully PATCH the recovered merchant's own row; the other merchant remains unchanged. This synthetic status change is **not** evidence of a signed real subscription-provider payment or entitlement.
