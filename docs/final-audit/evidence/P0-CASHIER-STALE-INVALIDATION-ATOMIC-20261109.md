## Verified second race bug (distinct from successful /station/me stale hydration fix)

`CashierOperatorGate` previously responded to `CASHIER_STATION_CREDENTIAL_INVALID` or `CASHIER_STATION_PAIRING_REQUIRED` by calling `clearInvalidCashierStationBinding()` **without identifying the original request's merchant/station/token/device**. The function read the *current* IndexedDB identity and unconditionally deleted the station binding. If another tab or the same device had already re-paired while an old HTTP request was pending, the old rejected request could erase the newer successful pairing.

**Actual RED** on native Chromium and real IndexedDB [#42642136673](https://github.com/nora953/fawri-production-source/actions/runs/42642136673), pre-fix [`638f00cc`](https://github.com/nora953/fawri-production-source/commit/638f00cc59753524e75af5198192a197bda35aea): a later station and token were committed, but invoking the invalidation response for the earlier station yielded `P0_STATION_BINDING_RACE: stale invalid-credential response must not clear later pairing`. The old response was synthetic; the bootstrap store/transactions and production recovery function ran in real Chromium.

## Correction and proof

- Introduced a dedicated `clearCashierStationBindingIfMatches(expected)` in `cashierOperatorSessionRuntime.ts`. It uses a single **readwrite transaction** on the existing bootstrap database, reads the stored identity, and compares *all displayed merchant/station/device/token/location/branch/credential identity and policy fields* to the captured request binding. Missing/mismatching values cause **zero writes**, and a valid match deletes **only station binding fields**. It neither creates a new identity nor deletes local financial history/outbox.
- Kept the earlier metadata-only `writeCashierDeviceIdentityIfUnchanged` strict: it must refuse changing station/token identity. The first attempt [`1b7ae899`](https://github.com/nora953/fawri-production-source/commit/1b7ae899f5f3f40f0a713dcf284c21f2585564d6) attempted to use that metadata-only helper for revocation. [Chromium #42642712924](https://github.com/nora953/fawri-production-source/actions/runs/42642712924) correctly caught its `CASHIER_STATION_IDENTITY_UPDATE_UNSAFE` error. **This intermediate attempt was not accepted.** The separate atomic revocation helper in [`18d487cb`](https://github.com/nora953/fawri-production-source/commit/18d487cbb1b30aabfd7c8243916c8493cafb8a0f) fixed it.
- `CashierOperatorGate` now passes the **pre-request captured** `CashierStationBinding` into the invalidation handler during load, login and the end-shift button. A stale error cannot mutate a later station. No unscoped fallback is allowed. A valid *current* invalid-token response can still unpair safely.
- First GREEN [Chromium #42643296608](https://github.com/nora953/fawri-production-source/actions/runs/42643296608) **SUCCESS**, including the native outbox + stale-backup regressions, but unrelated TypeScript consumers revealed that the end-shift callback needed the captured binding argument too. That callsite was corrected in final exact SHA `75fbf317`; [Chromium #42643829722](https://github.com/nora953/fawri-production-source/actions/runs/42643829722) **SUCCESS** and frontend typecheck in Auth OTP continuity **SUCCESS**.
- Browser GREEN marker `P0_STATION_BINDING_RACE_REAL_INDEXEDDB`: `old_http_response_overwrite_denied=true`, `new_station_preserved=true`, `stale_transaction_cas_denied=true`, `matching_original_station_hydrated=true`, `canonical_device_identity_preserved=true`, **`stale_invalid_credentials_did_not_clear_new_binding=true`**, **`current_invalid_credentials_cleared_only_station=true`**. This is a genuine RED/GREEN acceptance with production TypeScript functions and real Chromium IndexedDB, using a synthetic network response to control timing.
- Regression contract checks fail if future code calls unscoped `clearInvalidCashierStationBinding()` or drops the captured request binding from any current gate callsite.
